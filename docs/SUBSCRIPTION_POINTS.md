### 2.2 一次生成實際會送多少 token

由程式實測與推估（`apps/api/src/generation/`）：

| 項目 | 數值 | 依據 |
| --- | --- | --- |
| 出題系統提示 | **7,831 tokens**（29,697 字元） | 實測 `QUESTION_SKILL` + `FIGURE_SKILL` |
| 每批題數 | 6 題 | `QUESTIONS_PER_CALL = 6` |
| 每批素材上限 | 14,000 字 ≈ 8,750 tokens | `BATCH_MATERIAL_CHARS = 14_000`，中文 1.6 字/token |
| 題目輸出 | 約 450 tokens/題 | 混合題型；程式題較高、選擇題較低 |
| 視覺規劃 | 3,000 + 250×題數 input；150×插圖 output | 第二趟 planning call |
| 插圖 | 每 3 題約 1 張 | `imageMode: auto` 的預設行為 |
| 緩衝 | ×1.2 | 重試、修復、驗證與批次拆分 |

10 題一份的實際帳：2 次出題呼叫（每次 5 題）＋1 次視覺規劃，約 **22k input / 5k output**。

成本公式：

```
成本(US$) = (輸入 tokens × 輸入單價 + 輸出 tokens × 輸出單價) ÷ 1,000,000 × 1.2
          + 插圖張數 × 0.00063
```

（單價見 2.1，全部用尖峰價；1.2 是重試緩衝。）

## 3. 點數制度

### 3.1 點值

- **1 點 = 1 題 DeepSeek Flash**（US$0.01）。方案內含點數是折扣後的點數，不是另一種貨幣。
- 付費方案的 AI 動作都扣點；免費方案目前沒有 AI 出題，因此沒有免費題數可用。
- 付費方案解鎖 DeepSeek Flash／V4 Pro 與生圖；點數決定「能用多少」。
- 只設一個點數錢包（不分 AI 點 / 圖片點）。理由：使用者不會算兩種幣、客服爭議少、
  圖片用量本來就小（成本占比不到 1%），用「每月 AI 生圖配額」當會員福利即可；
  Render 圖表由應用程式繪製，成本為 0，不佔這份配額。

### 3.3 為什麼是這些數字

- **每題 0 / 1 / 4 點**：免費模型 0 點用來拉新；DeepSeek Flash 1 點是付費入門，
  成本 $0.00184/題；Pro 4 點（$0.04/題）仍低於一份 10 題 $0.40 的心理關口。
- **Pro = Flash ×4**：供應商價格比約 3.5 倍（輸入 4.5 倍、輸出 3.37 倍），向上取整為 4，
  確保 Pro 不會因為四捨五入而補貼；模型換價時只改一個常數。
- **生圖 10 點**：成本幾乎為零，價格是為了**抑制無意義重試**與維持會員價值感；
  配合每月配額，正常使用者幾乎不會被扣到。
- **Render 圖表 0 點、不限**：函數、幾何、圖表、地圖、電路、分子等由應用程式依結構化
  資料即時繪製，成本為 0，**所有方案（包括免費）**都有，也**不計入**方案的每月 AI 生圖配額；
  只有真正的 AI 生成圖片才需要配額或點數，包括出題時生成的相片。
- **素材附加費**：反映輸入 token，但用級距而非逐字計價，使用者才看得懂。
- **不設最低消費**：1 題 Flash 就是 1 點，所見即所付。

## 7. 規則設計

### 7.1 扣點流程

1. 使用者按下生成前，先顯示**預估點數**（例：10 題 DeepSeek Pro＋3 萬字素材 = 55 點）。
2. 伺服器先**保留**上限點數（避免併發超扣）。
3. 生成完成後**結算**：依實際交付題數扣點，未交付部分退回。
4. 圖片只在使用者看到成功結果時才扣點。

### 7.2 失敗與退款

| 情況 | 處理 |
| --- | --- |
| 供應商完全失敗、0 題 | 全額退點，不扣手續 |
| 部分成功（API 回 partial） | 只扣已交付題數，其餘退回 |
| 使用者中途取消 | 扣已交付題數 |
| 生圖失敗 | 不扣點 |
| 重複扣點（網路重送） | 以請求 id 冪等，只扣一次 |

### 7.3 點數有效期

| 點數來源 | 規則 |
| --- | --- |
| 免費方案 | 不發點數 |
| 方案點數 | 每月重置為方案點數（500／1,100／2,500）；未用完不累積，也不補發錯過的月份 |
| 加購點數 | 購買日起 12 個月；不受每月重置影響 |
| 訂閱到期 | 方案點數不再可用；帳戶回落免費方案（每月 200 題 GLM-4.7-Flash）。重新訂閱時以新方案點數覆蓋，加購點數保留 |

扣點順序：先扣**方案點數**→ 再扣**加購點數**。

方案點數的重置由資料庫在「讀取餘額或扣點」時惰性執行（lazy reset），不需要
cron 或前端計時器；詳見 §7.7。

### 7.4 退款

- 首次成功付款 7 天內，可從「帳戶」頁面申請；每個訂閱只可退款一次。API 是
  `GET /api/billing/refund`（報價）與 `POST /api/billing/refund`（執行）。
- 月繳：`退款 = 實付金額 × 未使用方案點數 ÷ 每月方案點數`。例如 $4.99／500 點，
  用了 100 點，退款 = 4.99 × 400 ÷ 500 = **$3.99**。
- 年繳：`退款 = 實付金額 ×（11 + 未使用點數 ÷ 每月點數）÷ 12`。未使用的完整未來月份
  全額退還，當前月份按未使用點數比例計算；完全未使用即全額。
- 未使用 0 點（月繳）或已過 7 天：不能自動退款，畫面會說明原因並引導聯絡支援；
  仍可在 Stripe Portal 取消，使用至已付期間結束。
- **加購／贈送點數**不計入公式，亦不可退款；退款只按方案每月點數計算。
- 退款成功後即時取消 Stripe 訂閱、清除剩餘方案點數、帳戶回到 Free；`billing_refunds`
  記錄退款，`billing_finalize_refund` 以同一交易完成降級。延遲送達的訂閱 webhook 會被
  `private.billing_keep_refunded` 擋住，不會重新發點或恢復付費方案。
- Stripe 的 `charge.refund.updated` 會更新 `billing_refunds.status`（`pending` /
  `succeeded` / `failed` / `canceled` / `requires_action`）及 `failure_reason`。若退款
  非同步失敗，Account 頁會顯示「退款失敗，款項可能尚未退回」，需要人工跟進；系統不會
  自動恢復已取消的訂閱。
- **點數不得兌換現金**，退款以該筆實付金額為上限，避免用方案點數套利或超額退款。
- **刪除帳號**：前端先呼叫 `POST /api/billing/cancel` 讓 Stripe 在當期結束時停止續訂，
  再刪除 Supabase 帳號；刪除帳號本身不會退款，應先跑退款流程。
- 退款政策在 `#/docs`、`#/docs/refunds`、`#/docs/billing` 與《服務條款》保持一致；
  上線前仍應請法律確認當地消費者保護法規。

### 7.5 公平使用

本版**沒有每日生成次數上限**；仍保留速率與帳號層面的防濫用規則，目的不是收費：

- 免費：**每個日曆月 200 題**、單次最多當月剩餘題數、不能 AI 生圖（Render 圖表仍可用）；短時間內大量請求會被速率限制。
- 付費：單次題數不限，點數不足即拒絕；每分鐘最多 3 次生成，異常用量進入人工審核。
- 短時間內大量註冊、退款後重複註冊：暫停帳號或限制功能。

### 7.6 上線銜接

- 現有帳號自動轉為免費方案（GLM-4.7-Flash，每月 200 題）；DeepSeek 與 AI 生圖改為需訂閱，Render 圖表仍可用。
- 既有題目、素材與儲存空間不受影響；只有「新生成」開始扣點。
- 上線前 30 天公告新制與點數規則。

### 7.7 每月重置在哪裡執行（Cloudflare Workers 部署）

**不需要 cron，也不需要 Cloudflare Queues／Durable Objects。** 網站是 Workers +
Supabase 時，權威資料在 Postgres；重置就放在 Postgres 的 security-definer RPC 裡，
任何一次讀餘額或扣點都會先檢查：

```
billing_snapshot / billing_spend / billing_image_take
        │
        ▼
  private.billing_apply_reset(uid)
        │  row lock（select … for update）
        ▼
  now() >= points_reset_at ?
        │ yes
        ▼
  會員仍有效（active／trialing 且 period_end > now()）？
        │ no                              │ yes
        ▼                                 ▼
  points = 0                     points = monthly_points
  reset_at = null                images_used = 0
  （不發點、不再排程）            reset_at += 1 month（跳過 missed months）
                                 ledger: reset:<epoch>
```

- **只訂一個月／到期當下**：`period_end > now()` 在時間相等時為 false，所以週年那一刻
  不會被當成新的一個月；到期後的重置只會清掉方案點數，不會發新點。
- **延遲的續訂 webhook**：過期重置會把 `points_reset_at` 設回 null，續訂事件因此不會被
  誤判為「本月已發過」；`invoice.paid` 一到就補發當月點數。
- **年繳**：Stripe 一年只開一次 invoice，但 `points_reset_at` 是「上次重置 + 1 個月」，
  所以照樣每月重置，不會一年只發一次。
- **多裝置／併發**：`billing_row` 先 `for update` 鎖住該帳戶，第二個請求會排隊並看到
  已更新的 `points_reset_at`，因此只會重置一次。
- **一個月沒登入**：下次登入只拿「當月」點數；`while next_reset <= now()` 會直接跳到
  下一個未來日期，不補發。
- **前端**：只顯示 `pointsResetAt`／`monthlyPoints` 與下次重置日；不自行加點、
  不改 localStorage、不用系統時間判斷到期。
- 若之後真的需要「每月 1 日全站統一重置」或報表，才需要 Cloudflare Cron Trigger；
  本版規則（訂閱週年重置）不需要。

### 7.8 方案變更（Customer Portal）

- Portal 更新的是訂閱 item 的 **price**，不會改寫 Checkout 寫入的 `metadata.plan`；
  webhook 因此以 price 對應方案，metadata 只在 price 不在本站目錄時才 fallback。
- **升級**：即時生效，Stripe 按比例收差額（proration）。資料庫把方案點數補到新方案，
  但只加差額：Light 500 → Standard 1,100 加 600，已用掉的點不會補回。
- **降級**：Portal 設為 period end 才生效；本期仍用原方案與原點數，到期後才換方案。
- 同一 period 內重複的 webhook 用 `plan-change:<sub>:<period>:<plan>` ledger key 去重，
  不會重複補點。
- 方案頁的「Change plan」會導到 Portal；不要在有效訂閱期間再開一次 Checkout。

`/api/billing/me` 回傳 `planPoints`、`bonusPoints`、`monthlyPoints`、`pointsResetAt`；
Account 頁只負責顯示。前端即使改時間或 localStorage 也無法加點，因為
`billing_snapshot`／`billing_spend` 的餘額完全由資料庫計算。
